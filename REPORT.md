## 2. Мета роботи

Метою роботи було пройти повний шлях від створення репозиторію й
налаштування інфраструктури до робочої версії консольної програми, яку
можна відтворено зібрати й запустити на різних операційних системах.

У межах роботи досягнуто:
- створено Java-проєкт із системою збирання Maven;
- підключено залежність JUnit 5 через pom.xml без копіювання бібліотеки
  в репозиторій;
- організовано код, тести та дані в репозиторії GitHub;
- реалізовано читання текстових записів, їх перевірку та базові числові
  обчислення;
- реалізовано форматований вивід результату в консоль і текстовий файл;
- налаштовано запуск збірки, тестів і статичного аналізатора через
  Maven Wrapper;
- організовано роботу через GitHub Issues і Pull Request.

## 3. Постановка задачі

Формат одного запису у `data/input.csv` (роздільник `;`, кодування
UTF-8):

```
name:String; group:String; course:int; average:double; scholarship:boolean
```

Показники, які обчислює програма:

1. Кількість коректних записів.
2. Середній бал (`average`) серед коректних записів.
3. Найбільший бал (`average`) серед коректних записів.
4. Кількість стипендіатів (`scholarship == true`).

Рядок вважається хибним і пропускається (з поясненням причини та номера
рядка), якщо:
- він порожній;
- кількість полів не дорівнює 5;
- ім'я або назва групи порожні;
- поле `course` або `average` не є числом;
- `course` або `average` від'ємні.

`--input`, `--output`), зчитує рядки з `data/input.csv` через

`buildReport`, який послідовно виконує для кожного рядка перевірку

(`System.out.print`) і записується у файл через `Files.writeString`.

## 5. Інфраструктура

- **Збірка:** Maven, керований через Maven Wrapper (`./mvnw`) — глобальна
  установка Maven на машинах, що збирають проєкт, не потрібна.
- **Залежності:** `org.junit.jupiter:junit-jupiter:5.12.2` підключено зі
  scope `test`, підтягується автоматично через `pom.xml`.
- **Статичний аналізатор:** SpotBugs (`spotbugs-maven-plugin:4.9.7.0`),
  прив'язаний до фази `verify`. Під час першого запуску `verify`
  аналізатор знайшов помилку `NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE`
  (можливий null pointer через подвійний виклик `output.getParent()`).
  Помилку виправлено — результат `getParent()` збережено в окрему
  змінну перед перевіркою на `null`. Після виправлення `./mvnw clean
  verify` завершується з `BUILD SUCCESS`, `BugInstance size is 0`.
- **Пакування:** `maven-shade-plugin:3.6.0`, прив'язаний до фази
  `package`, формує виконуваний jar із залежностями
  (`lab01-1.0.0-shaded.jar`) з головним класом `ua.lpnu.kzp.Main`.

## 11. Відповіді на контрольні питання

<!-- ЗАПОВНІТЬ власними словами. Нижче — стислі підказки-нагадування,
не готові відповіді для копіювання: -->

1. **pom.xml** — описує координати проєкту (groupId, artifactId,
   version), версію Java, кодування, залежності та плагіни збірки.
2. **test / verify / package** — кожна наступна фаза виконує всі
   попередні: `test` компілює й запускає тести, `verify` додатково
   запускає статичний аналізатор, `package` додатково формує JAR.
3. **Maven Wrapper** — дозволяє збирати проєкт без попередньо
   встановленого Maven у системі; версія Maven фіксується в
   репозиторії.
4. **main** — точка входу програми, з якої JVM починає виконання.
5. **Примітивний тип vs String** — примітивні типи зберігають значення
   безпосередньо (int, double, boolean тощо), `String` — посилальний
   тип, об'єкт з додатковою функціональністю.
6. **double для середнього** — цілочислове ділення (int/int) відкидає
   дробову частину; явне приведення до `double` цього не робить.
7. **`Integer.parseInt("abc")`** — кидає `NumberFormatException`.
8. **Мовчазний пропуск рядка** — приховує реальні проблеми даних; звіт
   має пояснювати причину й номер рядка.
9. **`split(";", -1)`** — зберігає порожні кінцеві поля замість їх
   відкидання.
10. **`Path.of` замість конкатенації** — обирає правильний роздільник
    шляху для поточної ОС (Windows/`\`, Unix/`/`).
11. **`StandardCharsets.UTF_8`** — гарантує однакове читання
    україномовного тексту незалежно від локалі ОС.
12. **`%n` vs `\n`** — `%n` вставляє роздільник рядка, властивий
    поточній ОС; `\n` завжди вставляє Unix-переведення рядка.
13. *(відповідь за власним варіантом — див. розділ 3 цього звіту)*
14. **Тести обчислення середнього** — перевірка з кількома коректними
    записами й порівнянням очікуваного середнього з допустимою похибкою
    (`assertEquals(expected, actual, 0.0001)`).
15. **Статичний аналізатор** — виявляє потенційні дефекти в
    скомпільованому байт-коді (наприклад, можливі null pointer
    dereference), які компілятор не вважає помилкою.
16. **GitHub Actions** — автоматично запускає збірку й перевірки на
    кількох ОС при кожному push/PR (continuous integration).
17. **GitHub Issue на дефект** — має містити кроки відтворення,
    очікуваний і фактичний результат.
18. **Академічна доброчесність у звіті** — назва інструмента ШІ, ролі й
    промпти, прийняті рекомендації, виправлені помилки, підтвердження
    розуміння коду.
19. **DevOps vs Валідатор** — DevOps консультує щодо інфраструктури
    збірки (Maven, аналізатор, CI); Валідатор шукає крайові випадки й
    оформлює дефекти, не займаючись інфраструктурою.
20. Напевне це буде чому Double.NEGATIVE_INFINITY використовується для поушку середньої
    оцінки адже начебто можна було взяти 0, але якби оцінки задавались -4 і т.д.
    це викликало б помилку (через порівння max) тому було приняте рішення
    таке рішення 

## 12. Висновки

У результаті роботи створено першу версію консольного продукту для
предметної області «Реєстр студентів» (варіант 6). Програма читає
записи з `data/input.csv`, відкидає хибні рядки з поясненням причини та
номера, обчислює чотири показники варіанта та формує звіт одночасно в
консоль і файл `out/report.txt`. Інфраструктура проєкту (Maven Wrapper,
JUnit 5, SpotBugs, maven-shade-plugin) забезпечує відтворювану збірку
через єдину команду `./mvnw verify`/`./mvnw package`. Робота
організована через GitHub Issues і Pull Request із зв'язком через
`Closes #N`.

Репозиторій підготовлено так, щоб у лабораторній роботі № 2 рядкові
записи (`String[] fields`) можна було замінити власними класами без
зміни зовнішньої поведінки програми — вся логіка розбору, перевірки й
обчислення вже ізольована в окремому методі `buildReport`.
